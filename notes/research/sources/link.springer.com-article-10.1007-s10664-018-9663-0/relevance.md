# Relevance — Mock objects for testing java systems: Why and how developers use them, and how they evolve (Spadini, Aniche, Bruntink, Bacchelli)

**Verdict:** relevant — peer-reviewed mixed-methods empirical study (Empirical Software Engineering, 2019) characterizing *which dependencies developers mock, why, and how mocks evolve* across four Java systems. It supplies measured, generalizable evidence on mocking strategy — one of the testing-technique categories named in the rubric — even though the code under study is human-authored, not LLM-authored.

## Salient sections

- **What to mock vs. not mock (RQ1 + interviews/survey).** Mocking is "highly dependent on the responsibility and the architectural concern of the class": developers mock dependencies that make testing hard (infrastructure — DB, web services, external resources) and *avoid* mocking classes that encapsulate domain concepts/rules. Survey "always/almost always mock": web services ~82%, external deps ~79%, databases ~71%; native Java libraries 82% never/almost-never. → For LLM-authored code this argues a default strategy: mock the slow/external boundary, exercise domain logic against real objects.
- **Integration boundary is left un-mocked (D1 quote).** "I do not mock when I want to test the database itself; I want to make sure that my SQL works." → Strategy implication: keep the I/O/persistence layer in real integration tests rather than mocking it.
- **Mocking's cost — coupling and maintenance.** Reported key challenges: keeping mock behavior compatible with the original class is hard, and mocking "increases the coupling between the test and the production code." Evolution data: of mock changes, **51% were forced by production-code changes** vs 49% test improvements; production-API changes forcing mock edits include method renamed 30%, parameter count 27%, return type 13%. → Quantifies the test-fragility tax of heavy mocking, relevant when LLM-generated tests over-mock.
- **Mocks can hide design/bugs (D3, D4 quotes).** A lead: "I do not remember a single case in which I found a bug using mocks"; the Mockito core developer: mocking many dependencies is "a big red flag that the unit under test is not well designed." → Caution against mock-heavy LLM test suites that pass without exercising real behavior.
- **Mocks are sticky (RQ4, Table 5, N=2,935).** **83%** of mocks are introduced at the test class's inception and tend to persist for its lifetime; only 17% added later, 13% later removed. → Early test-design choices about mocking largely lock in; matters for how LLM scaffolding seeds a suite.
- **Realism vs. focus framing (verbatim).** "By testing all dependencies together, developers gain realism. By simulating its dependencies, developers gain focus." → The core strategy trade-off to balance.
- **Null result on code metrics.** Despite developers saying they mock complex/highly-coupled classes, CK-style metrics (CBO, complexity, LOC, NOM) did **not** explain mocking decisions (differences mostly negligible: Cliff's Delta < −0.12). → Mocking decisions are driven by architectural role, not measurable complexity alone.

## Evidence weight

- **Study type:** Mixed-methods empirical — static analysis (custom MockExtractor tool), manual categorization, 3 developer interviews, 105-developer survey, git-history mining, plus a Mockito core-developer interview. Statistics: Wilcoxon rank-sum (95%), Cliff's delta, Shapiro-Wilk.
- **Scope/sample:** Four Java systems (3 OSS: Sonarqube, Spring, VRaptor; 1 industrial: Alura), all Mockito. 4,419 test units; 38,313 dependencies (6.71% mocked); manual sample 2,178 dependencies, inter-rater agreement 89%.
- **Caveats / not on LLM code:** General SE study of **human-written Java/Mockito** code — applies to LLM-authored code only by analogy, not direct measurement. Java/Mockito-only; survey skews to South America (66%) and the authors' networks; only 3 interviews; static analysis misses dynamically-generated mocks; line-matcher precision ~73%; the code-quality metrics are admittedly insufficient. Descriptive of mocking *practice*, not a controlled comparison of mock-vs-no-mock fault detection.
